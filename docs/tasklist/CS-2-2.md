# Tasklist: CS-2-2 -- YAML Parsing for Flutter Module Name Extraction

**Ticket:** CS-2-2
**Status:** IMPLEMENT_STEP_OK
**Created:** 2026-03-01

## Context

Phase 2 adds module support for Flutter projects. CS-2-2 implements YAML parsing to extract the `name:` field from `pubspec.yaml` files and insert Flutter module names into the `modules` SQLite table. This ticket depends on CS-2-1 (adding `pubspec.yaml` to `is_module_file()`).

The implementation adds `serde_yaml = "0.9"` to `Cargo.toml` and adds a new branch inside `index_modules_from_files()` in `src/indexer.rs`, following the established branch-by-filename pattern used for Gradle, SPM, and Perl modules.

---

## Tasks

- [x] **Task 1: Add `serde_yaml` dependency to `Cargo.toml`**

  Add `serde_yaml = "0.9"` to the `[dependencies]` section, placed immediately after the existing `serde_json = "1"` line.

  **Acceptance criteria:**
  - `Cargo.toml` contains `serde_yaml = "0.9"` in `[dependencies]`, positioned after `serde_json = "1"`.
  - `cargo build` succeeds with the new dependency resolved.

- [x] **Task 2: Implement `pubspec.yaml` branch in `index_modules_from_files()` (`src/indexer.rs`)**

  Add a new branch that checks `name_str == "pubspec.yaml"`, reads the file, deserializes it via `serde_yaml::from_str::<PubSpec>()` using a local `#[derive(serde::Deserialize)] struct PubSpec { name: Option<String> }`, and inserts `(name, module_path)` into the `modules` table via `INSERT OR IGNORE`.

  **Acceptance criteria:**
  - Running `ast-index index` on a Flutter project with `pubspec.yaml` containing `name: my_app` results in `ast-index modules` listing `my_app` with the correct relative directory path (Scenario 1).
  - A `pubspec.yaml` lacking a `name:` field (or with malformed YAML) is silently skipped -- no error is returned and no module row is inserted (Scenario 3).

- [x] **Task 3: Verify graceful handling of edge cases**

  Confirm that: (a) a `pubspec.yaml` with a complex structure (many fields) only extracts `name:` and ignores all other fields; (b) a root-level `pubspec.yaml` produces an empty string as the module path, which is acceptable.

  **Acceptance criteria:**
  - Parsing a `pubspec.yaml` containing `version:`, `description:`, `dependencies:`, etc. alongside `name: feature_auth` inserts only `feature_auth` as the module name, with no extraneous data (Scenario 4).
  - Root-level `pubspec.yaml` produces a module row with an empty path string and the correct name from the YAML `name:` field.

- [x] **Task 4: Verify no regressions in existing module parsers**

  Run the full test suite and confirm that Gradle (`build.gradle`, `build.gradle.kts`), SPM (`Package.swift`), and Perl (`.pm`) module parsing are unaffected by the new branch (Scenario 5).

  **Acceptance criteria:**
  - `cargo test` passes with zero failures.
  - A project containing `build.gradle`, `Package.swift`, and `pubspec.yaml` has all three module types indexed correctly after `ast-index index`.

- [x] **Task 5: Lint, format, and build validation**

  Run `cargo clippy -- -D warnings`, `cargo fmt --check`, and `cargo build --release` to confirm compliance with project code style and zero new warnings.

  **Acceptance criteria:**
  - `cargo clippy -- -D warnings` reports zero new warnings.
  - `cargo fmt --check` exits with code 0 (no formatting changes required).
