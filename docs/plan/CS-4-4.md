## Scope

CS-4-4 is the final quality gate for Phase 4 (Testing & Verification). It requires running three lint/format verification commands and one test command, fixing any issues found, and confirming a fully clean build. The four commands are:

1. `cargo clippy -- -D warnings` -- zero warnings in production code
2. `cargo clippy --tests -- -D warnings` -- zero warnings in test code
3. `cargo fmt --check` -- zero formatting differences
4. `cargo test` -- all tests pass green

This task covers all Flutter/Dart code from Phases 1-3 and all test code from Phase 4 tasks 4.1-4.3.

## Implementation Tasks

### Task A: Run Initial Clippy Verification (Production)

```bash
cargo clippy -- -D warnings
```

**Expected outcome:** Exit code 0 with "Finished dev profile" and no warning output.

**If warnings are found:**
- Address each warning by modifying the source code to satisfy clippy's suggestion.
- Do NOT add `#[allow(clippy::...)]` attributes (PRD Constraint 4).
- Do NOT change functional behavior (PRD Constraint 3). If a clippy suggestion would alter semantics, skip it and document the reasoning.
- Three pre-existing `#[allow(...)]` annotations are permitted to remain as-is:
  - `src/commands/android.rs:90` -- `#[allow(clippy::type_complexity)]`
  - `src/commands/ios.rs:61` -- `#[allow(clippy::type_complexity)]`
  - `src/commands/project_info.rs:363` -- `#[allow(clippy::too_many_arguments)]`

### Task B: Run Clippy Verification (Including Tests)

```bash
cargo clippy --tests -- -D warnings
```

**Expected outcome:** Exit code 0 with no warnings for test code.

**If warnings are found in test code:**
- Apply the same fix approach as Task A.
- Common test-code warnings: unused variables, unnecessary `clone()`, redundant type annotations.
- Fix the underlying issue rather than suppressing.

### Task C: Run Formatting Verification

```bash
cargo fmt --check
```

**Expected outcome:** Exit code 0 with no output (all files already formatted).

**If formatting issues are found:**
1. Run `cargo fmt` to auto-fix all formatting.
2. Re-run `cargo fmt --check` to confirm the fix.
3. Review the changes to ensure no unintended modifications (e.g., macro formatting edge cases).

### Task D: Run Full Test Suite

```bash
cargo test
```

**Expected outcome:** Exit code 0, all 398+ tests pass (0 failures, 0 ignored that should not be ignored).

**If tests fail after lint fixes:**
- The lint fix introduced a behavioral regression. Revert the specific fix and find an alternative approach that satisfies clippy without changing behavior.
- Re-run Tasks A-C after any revert to ensure they still pass.

### Task E: Document Clean Pass

Record the final verification results:
- Toolchain version (`rustc --version`, `cargo clippy --version`)
- Exit codes and summary output for all four commands
- Number of warnings fixed (if any)
- Number of tests passed

## NFR (Non-Functional Requirements)

1. **Zero warnings policy:** Both `cargo clippy -- -D warnings` and `cargo clippy --tests -- -D warnings` must exit with code 0 and produce zero warning lines in stderr.
2. **No suppression:** No new `#[allow(clippy::...)]` annotations may be added. The three pre-existing ones are acceptable.
3. **No behavioral changes:** Any clippy-driven refactoring must not alter the functional behavior of the code. If a suggestion would change semantics, it must be skipped and documented.
4. **Default formatting:** Use the project's default `rustfmt` settings (no `rustfmt.toml` overrides).
5. **Full test coverage maintained:** All existing tests must continue to pass. No tests may be deleted or `#[ignore]`d to achieve a clean pass.

## Risks

### 1. Nightly Toolchain Clippy Variance (LOW)

**Risk:** The project uses `channel = "nightly"` (`rustc 1.96.0-nightly 2026-02-28`). Nightly updates can introduce new clippy lints.

**Mitigation:** The research baseline was verified on the current nightly. If the nightly updates before task completion and introduces new lints, fix them following the same constraints (no suppression, no behavioral changes). Pin the nightly date in `rust-toolchain.toml` only as a last resort.

### 2. Cascading Changes from Lint Fixes (LOW)

**Risk:** A clippy fix in a core module (`indexer.rs`, `db.rs`) could affect downstream behavior.

**Mitigation:** Run `cargo test` after every individual fix (Task D). The 398-test suite provides strong regression coverage.

### 3. Code Added by Tasks 4.1-4.3 (LOW)

**Risk:** If tasks 4.1-4.3 add additional test code after the research baseline, that new code may introduce warnings or formatting issues.

**Mitigation:** CS-4-4 is explicitly designed to run after 4.1-4.3. Re-run all verification commands after any new code is integrated.

### 4. False Positive from Clippy (VERY LOW)

**Risk:** Clippy may flag an intentional code pattern (e.g., explicit type annotation for clarity).

**Mitigation:** Evaluate each warning individually. If a fix is genuinely harmful to readability, document the reasoning. Do not suppress without team consensus.
