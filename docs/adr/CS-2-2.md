# ADR: CS-2-2 -- YAML Crate Selection for Flutter Module Parsing

**Ticket:** CS-2-2
**Created:** 2026-03-01
**Status:** Decided

---

## Context

CS-2-2 requires adding a YAML parsing library to extract the `name:` field from `pubspec.yaml` files. The phase-2 description originally named `serde_yaml` as the crate to add. However, `serde_yaml` (by dtolnay) has been archived and is no longer maintained. Two replacement candidates exist: `serde_yml` (an active community fork) and `serde_yaml_ng` (another community maintenance fork with a stable 0.10.x release line).

The project already uses `serde = { version = "1", features = ["derive"] }` and `serde_json = "1"`, so any serde-based YAML library integrates naturally.

---

## Options

### Option A: `serde_yaml` v0.9 (dtolnay, archived)

**Pros:**
- Explicitly specified in the original phase-2 description and PRD
- Stable, well-tested codebase (v0.9.x)
- API is well-known in the Rust ecosystem
- Zero migration effort -- matches the description exactly

**Cons:**
- Repository archived, no new releases or bug fixes
- No security patches if vulnerabilities are discovered
- May eventually be yanked or conflict with future serde versions

### Option B: `serde_yml` v0.0.12+ (community fork, active)

**Pros:**
- Actively maintained with regular releases
- API is identical to `serde_yaml` for basic usage (drop-in replacement)
- Will receive bug fixes and security patches

**Cons:**
- Deviates from the explicit requirement in the phase-2 description
- Younger project with less community adoption (though growing)
- Version is still pre-1.0 (0.0.x), indicating API instability risk

### Option C: `serde_yaml_ng` v0.10.0 (community maintenance fork, active)

**Pros:**
- Actively maintained continuation of `serde_yaml` with the same API surface
- Version 0.10.x provides a stable, proven release line
- API is a drop-in replacement for `serde_yaml` -- identical for basic deserialization
- Addresses the archived/unmaintained concern of Option A without pre-1.0 instability of Option B
- Will receive bug fixes and security patches

**Cons:**
- Deviates from the original phase-2 description (which named `serde_yaml`)
- Smaller adoption than the original `serde_yaml`

---

## Decision

**Chosen: Option C -- `serde_yaml_ng` v0.10.0**

**Rationale:**
1. `serde_yaml` (Option A) is archived and will not receive security patches or compatibility updates. Using it introduces long-term maintenance risk.
2. `serde_yml` (Option B) is pre-1.0 and its API may change, introducing future churn.
3. `serde_yaml_ng` v0.10.0 provides the same API surface as `serde_yaml` while being actively maintained, making it the safest drop-in choice.
4. For the narrow use case of extracting a single `name:` field from YAML, the API difference is zero -- only the crate name and import path differ.
5. The implementation in `src/indexer.rs` uses `serde_yaml_ng::from_str::<PubSpec>(&content)`, which is identical in behavior to the `serde_yaml` equivalent.

**Migration path:** If `serde_yaml_ng` is ever abandoned, replace with `serde_yml` by changing `Cargo.toml` from `serde_yaml_ng = "0.10.0"` to `serde_yml = "0.0.x"` and updating import paths from `serde_yaml_ng::` to `serde_yml::`. The deserialization API is identical.
