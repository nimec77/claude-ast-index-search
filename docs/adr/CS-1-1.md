# ADR: CS-1-1 -- `has_build_marker()` Signature for Flutter Support

**Ticket:** CS-1-1
**Status:** Decided
**Created:** 2026-03-01

---

## Context

Task 1.4 of CS-1-1 requires `has_build_marker()` to return `true` for `pubspec.yaml` when `ProjectType` is `Flutter`. The current function signature is:

```rust
fn has_build_marker(path: &Path) -> bool
```

It does not accept a `ProjectType` parameter. The PRD (Constraints section, item 3) identifies this as a design decision to resolve during implementation.

---

## Options

### Option A: Add `pubspec.yaml` unconditionally (no signature change)

Append `|| path.join("pubspec.yaml").exists()` to the existing boolean chain.

**Pros:**
- Minimal change -- one line addition
- Consistent with existing pattern (e.g., `Makefile` is also a generic marker already in the list)
- No call-site changes required
- `pubspec.yaml` is sufficiently specific to avoid false positives

**Cons:**
- Non-Flutter sub-projects containing `pubspec.yaml` (pure Dart libraries) would also be detected, but this is actually correct behavior for monorepo sub-project detection

### Option B: Add `ProjectType` parameter to `has_build_marker()`

Change signature to `fn has_build_marker(path: &Path, project_type: ProjectType) -> bool` and conditionally check `pubspec.yaml` only when `project_type == ProjectType::Flutter`.

**Pros:**
- More semantically precise -- only checks Flutter markers for Flutter projects
- Future-proof for type-specific build markers

**Cons:**
- Broader refactor: requires updating the call site in `find_sub_projects()` which passes `pt` through
- Inconsistent with existing approach (current markers like `Makefile`, `CMakeLists.txt` are not guarded by project type)
- Over-engineering for the current use case

---

## Decision

**Option A: Add `pubspec.yaml` unconditionally.**

The function's purpose is to detect "does this subdirectory look like a project root" for monorepo sub-project detection. All existing markers (`ya.make`, `Makefile`, `BUILD`, `BUILD.bazel`, `CMakeLists.txt`) are added unconditionally regardless of project type. Adding `pubspec.yaml` the same way maintains consistency and keeps the change minimal.

`pubspec.yaml` is specific enough (only used by Dart/Flutter) that false positives in non-Flutter monorepos are not a realistic concern.

---

## Consequences

- `has_build_marker()` signature remains unchanged
- No call-site modifications needed in `find_sub_projects()`
- Any directory containing `pubspec.yaml` will be recognized as a sub-project boundary in monorepo detection, regardless of the parent project type
- If future requirements need type-conditional markers, the signature can be refactored at that time
