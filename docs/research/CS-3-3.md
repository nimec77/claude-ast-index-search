## Existing Patterns

### Platform-Specific Commands Table Format

All six existing initialize commands (`initialize-android.md`, `initialize-ios.md`, `initialize-web.md`, `initialize-rust.md`, `initialize-ruby.md`, `initialize-csharp.md`) follow an identical structure:

1. **Frontmatter** -- `name` and `description` fields
2. **Step 1: Check Prerequisites** -- `ast-index version` check
3. **Step 2: Create/Update .claude/settings.json** -- identical JSON block
4. **Step 3: Create .claude/rules/ast-index.md (CRITICAL)** -- rules file content with:
   - Mandatory Search Rules (identical across all)
   - Why ast-index (identical across all)
   - Command Reference table (3-column: Task | Command | Time)
   - **Platform-Specific Commands table** (2-column: Task | Command) -- THIS IS WHAT CS-3-3 ADDS
   - Index Management section (identical across all)
5. **Step 4: Build the Index** -- `ast-index rebuild`
6. **Step 5: Verify Setup** -- `ast-index stats` + platform-specific search term

The platform-specific commands table uses a **2-column `| Task | Command |` format** with no Time column.

## Valid CLI Subcommands for Flutter Examples

Based on `src/main.rs` (the Clap CLI definition), the following subcommands are relevant for Flutter/Dart examples:

| Subcommand | Purpose | Valid for Dart? |
|------------|---------|-----------------|
| `search` | Universal search (files + symbols) | Yes |
| `class` | Find class or interface | Yes (classes, mixins indexed as Interface, extensions as Object) |
| `symbol` | Find symbols by name | Yes |
| `implementations` | Find subclasses/implementors | Yes (extends/with/implements tracked) |
| `hierarchy` | Show class hierarchy tree | Yes |
| `usages` | Find usages of a symbol | Yes |
| `refs` | Cross-references | Yes |
| `callers` | Find callers of a function | Yes |
| `outline` | Show symbols in file | Yes |
| `imports` | Show imports in file | Yes |
| `module` | Find modules | Yes (pubspec.yaml indexed) |
| `deps` | Show module dependencies | Yes |
| `map` | Project overview | Yes |
| `conventions` | Architecture detection | Yes (detects BLoC, etc.) |

**IMPORTANT:** The `search` subcommand does NOT have `--kind` or `--lang` flags. The PRD (Constraint 4) explicitly calls this out. The phase-3.md description mentions `ast-index search --kind Class --lang dart` as an illustrative example, but this syntax is invalid. Examples must use `class` for class searches and `symbol` for other kinds.

**Also note:** There is no `modules` command (plural). The command is `module` (singular) and requires a pattern argument. The PRD Scenario 5 mentions `ast-index modules` but the correct command is `ast-index module "pattern"`.

## Dart Parser Capabilities

From `src/parsers/treesitter/dart.rs` and `references/dart-commands.md`, the Dart parser indexes:

| Dart Construct | SymbolKind | Searchable via |
|---------------|------------|----------------|
| `class ClassName` (all modifiers: abstract, sealed, final, base, mixin class) | Class | `class`, `search`, `symbol` |
| `interface class ClassName` / `abstract interface class` | Interface | `class`, `search`, `symbol` |
| `mixin MixinName` | Interface | `class`, `search`, `symbol` |
| `extension ExtName on Type` | Object | `search`, `symbol` |
| `extension type Name(Type _)` | Class | `class`, `search`, `symbol` |
| `enum EnumName` | Enum | `search`, `symbol` |
| `typedef Name = ...` | TypeAlias | `search`, `symbol` |
| Functions (methods, top-level) | Function | `symbol`, `callers` |
| Constructors, factory constructors | Function | `symbol` |
| Getters, setters | Function | `symbol` |
| Top-level variables (final/const/late/var) | Property | `symbol` |
| `import`/`export` statements | Import | `imports` |

### Inheritance Tracking

The Dart parser extracts parent relationships from:
- `extends` (superclass)
- `with` (mixins)
- `implements` (interfaces)
- `on` (mixin constraints)

This means `ast-index implementations "StatelessWidget"` will find all classes that extend StatelessWidget, `ast-index implementations "ChangeNotifier"` finds ChangeNotifier subclasses, etc.

## DEVIATIONS FROM REQUIREMENTS

1. **PRD Scenario 5 mentions `ast-index modules`:** The actual CLI command is `ast-index module "pattern"` (singular, requires a pattern argument). There is no `modules` (plural) subcommand. The examples must use `ast-index module "pattern"` instead.

2. **Phase-3.md mentions `ast-index search --kind Class --lang dart`:** As already documented in PRD Constraint 4, the `search` subcommand does not support `--kind` or `--lang` flags. The PRD correctly identifies this and says to use `class` subcommand instead. No deviation -- PRD already handles this.

3. **Web initialize-web.md uses invalid flag:** The existing `initialize-web.md` contains `ast-index search "use" --kind function` in its TypeScript/JavaScript-Specific Commands table. The `search` subcommand does not have a `--kind` flag. This is a pre-existing issue in the web initialize command and should not be replicated in the Flutter command.

## New Technical Questions Discovered During Research

1. **Should CS-3-3 implementation also fix the verify step search term?** The verify step (step 5) uses a platform-specific search term. PRD Scenario 6 says it should use `ast-index search "Widget"`. If CS-3-1 creates the file with a generic term, CS-3-3 may need to update it. This depends on what CS-3-1 produces.

2. **Table row count:** The PRD metric says "at least 8 task-command pairs". The proposed table above has 14 rows. Should this be trimmed to match the 6-8 row range used by other platform commands, or should it include more to better cover Flutter's breadth? The Android and iOS commands have 6 rows each, Ruby has 8, Web and C# have 5-6. Recommend 8-10 rows to cover the unique breadth of Flutter patterns (widgets, state management, Dart-specific constructs, modules) while staying consistent with the established pattern.
