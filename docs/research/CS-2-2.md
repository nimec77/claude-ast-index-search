**Ticket:** CS-2-2

## Summary

This ticket adds `serde_yaml` (or its maintained fork `serde_yml`) to `Cargo.toml` and implements YAML parsing in `index_modules_from_files()` to extract the `name:` field from `pubspec.yaml` files. The extracted name is inserted into the `modules` SQLite table, making Flutter modules visible via `ast-index modules`.

## Patterns Used

- **Branch-by-filename:** `index_modules_from_files()` uses `if name_str == "..."` chains to dispatch to the correct parsing logic for each module type.
- **Read-Parse-Insert:** Each branch reads the file content with `fs::read_to_string()`, extracts relevant data (regex or structured parsing), and inserts into the `modules` table with `INSERT OR IGNORE`.
- **Path derivation:** Module path is computed as `parent.strip_prefix(root).to_string_lossy()`. The parent directory of the module descriptor file becomes the module path.
- **LazyLock regex:** Static regex patterns use `LazyLock<Regex>` for one-time compilation.
- **serde deserialization:** The project already uses `serde` with `derive` feature and `serde_json`. Using `serde_yaml`/`serde_yml` for YAML deserialization follows the same ecosystem pattern.

### Step 2: Add pubspec.yaml branch to `index_modules_from_files()`

**File:** `/Users/comrade77/RustroverProjects/claude-ast-index-search/src/indexer.rs`

Add a new branch after the Maven block (line 1097) and before the closing `}` of the `if let Some(name)` block (line 1098). The implementation should:

1. Check if `name_str == "pubspec.yaml"`
2. Get the parent directory
3. Read the file content with `fs::read_to_string(path)`
4. Deserialize using `serde_yaml` into a minimal struct that captures only the `name` field
5. If the `name` field is present and non-empty, insert into the `modules` table

Example approach using a local struct:

```rust
// Flutter modules (pubspec.yaml)
if name_str == "pubspec.yaml"
    && let Some(parent) = path.parent()
{
    let module_path = parent
        .strip_prefix(root)
        .unwrap_or(parent)
        .to_string_lossy()
        .to_string();

    if let Ok(content) = fs::read_to_string(path) {
        #[derive(serde::Deserialize)]
        struct PubSpec {
            name: Option<String>,
        }
        if let Ok(pubspec) = serde_yaml::from_str::<PubSpec>(&content) {
            if let Some(ref name) = pubspec.name {
                if !name.is_empty() {
                    conn.execute(
                        "INSERT OR IGNORE INTO modules (name, path) VALUES (?1, ?2)",
                        rusqlite::params![name, module_path],
                    )?;
                    count += 1;
                }
            }
        }
    }
}
```

**Key decisions in this pattern:**
- The `PubSpec` struct uses `name: Option<String>` so that a missing `name` field does not cause a deserialization error -- it simply results in `None`, and the file is skipped.
- The struct is defined locally inside the branch to minimize scope, similar to how `PERL_PACKAGE_RE` is defined inside its branch.
- `serde_yaml::from_str::<PubSpec>()` failure (malformed YAML) is handled gracefully via `if let Ok(...)`.
- The module `name` comes directly from the YAML `name:` field (e.g., `my_app`), NOT from the directory path. This differs from the Gradle pattern (which derives module name from path) but matches the SPM pattern (which derives names from file content).
- The `module_path` uses the parent directory's relative path, consistent with all other branches.

## Limitations and Risks

1. **`serde_yaml` maintenance status (MEDIUM RISK):** The `serde_yaml` crate (v0.9.x) by dtolnay has been archived. The actively maintained fork is `serde_yml`. For the simple use case of extracting a `name:` field, both crates work identically. However, using an archived crate means no future bug fixes or security patches. The description file explicitly names `serde_yaml`, so it should be used unless the user confirms a switch to `serde_yml`.

2. **CS-2-1 is a prerequisite (BLOCKING):** The `is_module_file()` function does not yet include `pubspec.yaml`. Without CS-2-1, `pubspec.yaml` files will never be collected during the filesystem walk and will never reach `index_modules_from_files()`. The new code branch will exist but never execute. CS-2-1 must be completed first or concurrently.

3. **Module name uniqueness (LOW RISK):** The `modules` table has `UNIQUE` on `name`. If two `pubspec.yaml` files in a monorepo define the same `name:` value, the second one will be silently ignored by `INSERT OR IGNORE`. In practice, Flutter/Dart package names should be unique within a project, so this is unlikely to be an issue.

4. **Module path for root-level pubspec.yaml (LOW RISK):** If `pubspec.yaml` is at the project root, `parent.strip_prefix(root)` will produce an empty string `""`. This is the same behavior as the Gradle handler (which checks `!module_name.is_empty()` and skips empty names). For pubspec.yaml, the `name` comes from the YAML content, not the path, so the name will be populated even if the path is empty (`""`). An empty path for the root module is acceptable and consistent with SPM's handling.

5. **YAML parsing overhead (NEGLIGIBLE):** Parsing pubspec.yaml is a lightweight operation. Typical files are a few KB. The `serde_yaml` crate parses only what's needed when using `Option<String>` for unused fields.
