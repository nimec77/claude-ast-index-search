## 3. Patterns Used

### Guard Block Pattern (Task 5.2)

All 24 guard blocks follow the identical pattern:
```rust
if !db::db_exists(root) {
    println!(
        "{}",
        "Index not found. Run 'ast-index rebuild' first.".red()
    );
    return Ok(());
}
let conn = db::open_db(root)?;
```

**Confirmed locations (24 total):**
- `index.rs`: lines 33, 192, 245, 308, 363, 426 (6 occurrences)
- `management.rs`: lines 595, 691, 754, 807, 833 (5 occurrences)
- `modules.rs`: lines 26, 62, 135, 215 (4 occurrences)
- `android.rs`: lines 21, 129 (2 occurrences)
- `ios.rs`: lines 26, 121 (2 occurrences)
- `project_info.rs`: lines 197, 723 (2 occurrences)
- `files.rs`: line 50 (1 occurrence)
- `watch.rs`: line 16 (1 occurrence)
- `analysis.rs`: line 24 (1 occurrence)

**Variation analysis:** All 24 blocks are identical in structure: check `db::db_exists(root)`, print the same error message, return `Ok(())`. After the guard, they all call `db::open_db(root)?` to get a `Connection`. The proposed `open_db_or_warn(root: &Path) -> Result<Option<Connection>>` signature handles all of them uniformly -- return `None` when DB doesn't exist (after printing the warning), return `Some(conn)` when it does. Callers would use:
```rust
let conn = match db::open_db_or_warn(root)? {
    Some(c) => c,
    None => return Ok(()),
};
```

No deviations from the standard pattern were found.

### Row-Mapping Pattern (Task 5.3)

`SearchResult` is constructed from query rows in multiple places across `db.rs`. The struct has 5 fields (`name`, `kind`, `line`, `signature`, `path`), and identical row-mapping closures appear in:

- `search_symbols` (line ~481)
- `find_symbols_by_name` (line ~538)
- `find_class_like` (line ~643)
- `search_symbols_fuzzy` (line ~898)
- `search_symbols_scoped` (line ~985)
- `find_symbols_by_name_scoped` (line ~1041)
- `find_class_like_scoped` (line ~1094)
- `find_implementations` (separate function)
- Plus several more in command files (e.g., `analysis.rs` lines 74-95)

`RefResult` is constructed similarly in `find_references` and `find_references_scoped`.

Introducing `SearchResult::from_row(&rusqlite::Row) -> rusqlite::Result<SearchResult>` and `RefResult::from_row(&rusqlite::Row) -> rusqlite::Result<RefResult>` will eliminate all of these duplicated closures.

## 4. Limitations and Risks

### Task 5.4: `search_files` vs `search_files_limited`

`search_files` does NOT have early termination logic. `search_files_limited` has `AtomicUsize`-based counting and `AtomicBool`-based `should_stop`. Making `search_files` call `search_files_limited(root, pattern, extensions, usize::MAX, handler)` will introduce the early-termination atomic checks even for unlimited searches. This is negligible overhead (relaxed atomic loads) but worth noting.

The channel bound differs: `search_files` uses `channel::bounded(10000)` while `search_files_limited` uses `channel::bounded(limit.max(1000))`. With `usize::MAX` as limit, `limit.max(1000)` = `usize::MAX`, which is effectively unbounded. This should be addressed: the unified function should cap the channel bound at something reasonable (e.g., `limit.min(10000).max(1000)`) to avoid allocating a massive channel buffer.

### Task 5.8: Module Split and Rust 2024 Edition

The project already uses `edition = "2024"` in `Cargo.toml`. In Rust 2024, the module system uses file-based resolution: `src/indexer.rs` can serve as the parent module, and child modules go under `src/indexer/` (no `mod.rs` needed). This is the standard approach.

Key concern: Many functions in `indexer.rs` use private types (`ParsedFile`, `ModuleLookup`) and internal helpers (`parse_file`, `write_batch_to_db`, `is_module_file`, `EXCLUDED_DIRS`). When splitting into sub-modules, these need to be made `pub(crate)` or `pub(super)` and re-exported as needed.

The `WalkResult` struct is already `pub` and used by `commands/management.rs`.

### Task 5.8: Cross-Dependencies Between Sub-Modules

- `index_modules` and `index_module_dependencies` call `write_batch_to_db` (which would live in `files.rs` sub-module) -- but actually they don't; they do their own DB writes. `write_batch_to_db` is only called from `index_directory_scoped` and `index_node_modules_dts`.
- `index_node_modules_dts` uses `parse_dts_file` and `write_batch_to_db` -- these can both live in the `node_modules.rs` sub-module (with `write_batch_to_db` shared from `files.rs`).
- Several resource indexing functions reference `ModuleLookup` which should stay in the parent module.

### Task 5.9: db.rs Split (Optional)

The `queries.rs` sub-module would need to import `Connection`, `params`, and internal types. The `SearchScope` type builds SQL dynamically and is tightly coupled to the query functions. The split is straightforward: move all `search_*`, `find_*` functions plus `SearchResult`, `RefResult`, `SearchScope`, `DbStats` into `src/db/queries.rs`. Keep schema, `init_db`, `get_db_path`, `open_db`, `db_exists`, `delete_db`, `SymbolKind`, insert helpers, and extra-root functions in the parent.

### Dependency Verification: `grep-matcher` and `parking_lot`

- `grep-matcher = "0.1"` is listed in `Cargo.toml` line 17 but **never imported** anywhere in `src/`. Confirmed: `Grep` for `grep-matcher` in `src/` returned no results. Safe to remove.
- `parking_lot = "0.12"` is listed in `Cargo.toml` line 33 but **never imported** anywhere in `src/`. Confirmed: `Grep` for `parking_lot` in `src/` returned no results. Safe to remove.

### `#![allow(dead_code)]` in `db.rs`

Line 1 of `src/db.rs` contains `#![allow(dead_code)]`. Removing this will cause clippy/compiler to flag any genuinely dead functions. These must be reviewed and either removed or marked with `#[allow(dead_code)]` individually if there's a legitimate reason to keep them (e.g., planned future use).

## 6. New Technical Questions Discovered During Research

1. **Channel bound in unified `search_files_limited`:** When `limit = usize::MAX`, `limit.max(1000)` produces an enormous channel bound. Should the channel bound be capped (e.g., `limit.min(10000).max(1000)`)? This prevents accidental memory bloat.

2. **`SearchScope::none()` vs `SearchScope::empty()` naming:** The PRD says `empty()` but code has `none()`. Should the method be renamed for consistency, or should the implementation use the existing `none()` name?

3. **Dead code surfaced by removing `#![allow(dead_code)]`:** Which functions in `db.rs` will be flagged? The extent of cleanup is unknown until the attribute is removed and clippy is run. This may be a small or moderate amount of work.
