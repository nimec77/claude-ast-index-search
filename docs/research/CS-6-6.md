### Test Module Boundaries (Verified)

| File | `#[cfg(test)]` line | End line | Test lines | `use` in test |
|------|---------------------|----------|------------|----------------|
| `dart.rs` | L1095 | L1860 | 766 | `use super::*;` |

| `cpp.rs` | L574 | L1305 | 731 | `use super::*;` |
| `typescript.rs` | L803 | L1200 | 398 | `use super::*;` |

### Pattern to Use

Replace the inline test module with:
```rust
#[cfg(test)]
#[path = "<lang>_tests.rs"]
mod tests;
```

Each extracted `*_tests.rs` file will contain the test module body (without the outer `mod tests {` wrapper since the `mod tests;` declaration handles that), keeping `use super::*;` at the top.

### Risk: Test Import Scoping

All four test modules use `use super::*;`. Since the test module is still declared within the parent file (just with an external path), `super::*` will resolve to the parent module's items. This is a well-established Rust pattern. **No import changes needed in the test files themselves.**

However, the extracted test file content must be the **body** of the module, not wrapped in another `mod tests { }` block. The content should start with `use super::*;` and contain all `#[test]` functions directly.

## Task 6.3: Extract Dart Error Recovery Submodule

### Dependency: 6.1.1 Must Complete First

The error recovery code is at L854-1093. After test extraction (6.1.1), this becomes the code between L854 and the end of the non-test portion (L1094).

### Functions and Structs to Move (L854-1093, ~240 lines)

**Error recovery functions:**

- `ClassInfo` struct (L901)

- `try_parse_extension_type()` (L981)
- `extract_parents_from_error_text()` (L1021) -- called from `extract_class_or_enum()` at L464

**Helper functions also in the L854-1093 range that are used by non-error-recovery code:**
- `find_first_identifier()` (L1057) -- used at L612, L821, L840 (non-error-recovery contexts)
- `find_first_type_identifier()` (L1068) -- used at L396, L484 (non-error-recovery contexts)
- `find_descendant_by_kind()` (L1082) -- used at L159, L628, L629 (non-error-recovery contexts)

### CRITICAL FINDING: Shared Helper Functions

The PRD specifies moving "error recovery structs/functions from `dart.rs` (post-test ~L855-1093)". However, three functions in this range (`find_first_identifier`, `find_first_type_identifier`, `find_descendant_by_kind`) are NOT purely error-recovery code -- they are general-purpose helpers used throughout `dart.rs`.

**Resolution options:**
1. **Keep helpers in `dart.rs`, move only error-recovery-specific code (L854-1054) to the submodule.** The error recovery submodule would need `use super::{...}` to access these helpers plus `node_text`, `node_line`, `line_text`, `walk_body_declarations`, `SymbolKind`, `ParsedSymbol`. The helpers stay in `dart.rs`.
2. **Move all L854-1093 to the submodule and re-export helpers via `pub(super)`.** The error recovery module would expose `find_first_identifier`, `find_first_type_identifier`, `find_descendant_by_kind` with `pub(super)` visibility, and `dart.rs` would use `error_recovery::find_first_identifier(...)` etc.
3. **Move all L854-1093 and add `pub(super) use` re-exports.** Similar to option 2 but with re-exports in `dart.rs` so existing call sites don't change.

Option 1 is cleanest and safest: move only the error-recovery-specific functions (L854-1054, ~200 lines), keep the 3 general helpers (L1057-1093, ~37 lines) in `dart.rs`. The error recovery submodule uses `use super::` to access what it needs.

The error recovery submodule would need access to:
- `node_text`, `node_line`, `line_text` -- from `super::super` (the treesitter `mod.rs`)
- `walk_body_declarations` -- from `super` (dart.rs, L644)
- `SymbolKind` -- from `crate::db::SymbolKind`
- `ParsedSymbol` -- from `crate::parsers::ParsedSymbol`
- `find_first_identifier`, `find_first_type_identifier`, `find_descendant_by_kind` -- from `super` (remaining in dart.rs)

Since `walk_body_declarations` is currently a private function in `dart.rs`, it would need to be made `pub(super)` or `pub(crate)` for the error recovery submodule to call it.

### Expected Post-Extraction Size

`dart.rs` after 6.1.1 + 6.3.1: ~1094 - 200 = ~894 lines (or ~855 if all L854-1093 is moved per PRD). Either way, well under 1000.

## Task 6.4: Deduplicate `find_capture` Across 14 Parsers

### Dependency: 6.1.1-6.1.4 Must Complete First

The `find_capture` function in some files (cpp.rs, csharp.rs, typescript.rs) sits right before the `#[cfg(test)]` block. After test extraction, the function remains in the production code. No issues.

### Verification: All 14 Implementations Are Identical

Every `find_capture` across all 14 files has the exact same signature and body:

```rust
fn find_capture<'a>(
    m: &'a tree_sitter::QueryMatch<'a, 'a>,
    idx: Option<u32>,
) -> Option<&'a tree_sitter::QueryCapture<'a>> {
    let idx = idx?;
    m.captures.iter().find(|c| c.index == idx)
}
```

**No signature variations exist.** This eliminates Risk #2 from the PRD (signature variation across copies).

## Patterns Used

1. **Test file externalization pattern:** `#[cfg(test)] #[path = "<name>_tests.rs"] mod tests;` -- well-established Rust pattern for keeping test code in separate files while maintaining module structure.
2. **Submodule extraction pattern:** `#[path = "dart_error_recovery.rs"] mod error_recovery;` -- Rust path attribute for non-standard module file locations.
3. **Shared utility elevation:** Moving `find_capture` from 14 local definitions to one `pub(crate)` in the parent module.
4. **Binary crate module splitting:** Adding `mod cli;` to `main.rs` to create a sibling module in the binary crate (not the library crate).

## Limitations and Risks

### Resolved Risks

1. **find_capture signature variations (PRD Risk #2):** RESOLVED -- all 14 copies are byte-identical. No adaptation needed.
2. **Test import scoping (PRD Risk #1):** RESOLVED -- `use super::*;` works correctly with `#[path]` attribute since the module parent relationship is preserved.

### Active Risks

1. **Dart error recovery shared helpers (PRD Risk #4):** The helper functions `find_first_identifier`, `find_first_type_identifier`, and `find_descendant_by_kind` at L1057-1093 are used by both error-recovery and non-error-recovery code. They should NOT be moved to the error recovery submodule. Instead, keep them in `dart.rs` and move only L854-1054 (the truly error-recovery-specific code). Alternatively, move all of L854-1093 per PRD and re-export the helpers with `pub(super)`.

2. **`management.rs` size after 6.2.2:** Adding `cmd_install_claude_plugin` (52 lines) to `management.rs` (957 lines) brings it to ~1009 lines, slightly over the 1000-line threshold this phase aims to eliminate. This is acceptable since the function is a natural fit for management commands, and the file could be split further in a future phase if needed.

3. **`walk_body_declarations` visibility for error recovery submodule (PRD Risk #4):** This function is private in `dart.rs` but called by `try_recover_from_error` in the error recovery code. It must be made `pub(super)` if the error recovery code is moved to a submodule.

4. **Merge conflicts (PRD Risk #5):** This phase touches the largest files in the codebase. Should be done in a focused burst on a dedicated branch.
