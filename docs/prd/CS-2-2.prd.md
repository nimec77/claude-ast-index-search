# PRD: CS-2-2 -- YAML Parsing for Flutter Module Name Extraction

**Status:** PRD_READY
**Ticket:** CS-2-2
**Created:** 2026-03-01

---

## Context / Idea

**Arguments:** CS-2-2 docs/phase/phase-2.md

Phase 2 introduces module and dependency support for Flutter projects. This ticket (CS-2-2) focuses specifically on adding `serde_yaml` to `Cargo.toml` and implementing YAML parsing to extract the `name:` field from `pubspec.yaml` in `index_modules_from_files()`.

**From description file (`docs/phase/phase-2.md`):**

> **Phase 2 Goal:** Parse `pubspec.yaml` to extract the module name and dependencies.
>
> **Task 2.2:** Add `serde_yaml` to `Cargo.toml` and implement YAML parsing to extract `name:` field from `pubspec.yaml` in `index_modules_from_files()`

This task depends on CS-2-1 (adding `pubspec.yaml` to `is_module_file()`), which ensures that `pubspec.yaml` files are collected during the directory walk and passed to `index_modules_from_files()`.

Currently, `index_modules_from_files()` handles Android/Gradle modules (`build.gradle`, `build.gradle.kts`), iOS/SPM modules (`Package.swift`), and Perl modules (`.pm` files). There is no handling for `pubspec.yaml`. The `serde_yaml` crate is not present in `Cargo.toml` (only `serde` and `serde_json` are listed).

---

## Goals

1. Add the `serde_yaml` crate as a dependency in `Cargo.toml` to enable YAML parsing.
2. Implement YAML parsing logic in `index_modules_from_files()` that reads `pubspec.yaml` and extracts the `name:` field.
3. Insert the extracted Flutter module name into the `modules` SQLite table so that `ast-index modules` lists it.
4. Follow the established pattern used by existing module parsers (Gradle, SPM, Perl) within `index_modules_from_files()`.

---

## User Stories

1. **As a Flutter developer**, I want `ast-index modules` to display the module name defined in my `pubspec.yaml`, so that I can see my Flutter project listed alongside other indexed modules.
2. **As a developer maintaining a multi-module Flutter project**, I want each sub-project's `pubspec.yaml` name to be extracted and indexed, so that module-level queries return accurate results.
3. **As a contributor to `ast-index`**, I want YAML parsing to use a well-maintained library (`serde_yaml`), so that the parsing is robust and consistent with the existing `serde`-based ecosystem already in the project.

## Constraints

1. **Crate to add (per description file):** `serde_yaml` must be added to `Cargo.toml`.
2. **Function to modify (per description file):** `index_modules_from_files()` in `src/indexer.rs`.
3. **Database schema:** The `modules` table has columns `(id, name, path, kind)`. The Flutter module name from `pubspec.yaml` should be inserted with the `name` field from YAML and the relative path of the parent directory.
4. **Pattern consistency:** The implementation must follow the same branch-by-filename pattern used for Gradle, SPM, and Perl modules in `index_modules_from_files()`.
5. **YAML parsing scope:** Only the top-level `name:` field needs to be extracted in this ticket. Dependency parsing (`dependencies:` and `dev_dependencies:`) is handled separately in CS-2-3.
6. **`serde` already present:** The project already depends on `serde = { version = "1", features = ["derive"] }` and `serde_json = "1"`, so `serde_yaml` fits naturally into the existing dependency ecosystem.
7. **Dependency on CS-2-1:** This ticket assumes `pubspec.yaml` is already recognized by `is_module_file()` (task 2.1), so that `pubspec.yaml` files are collected and passed to `index_modules_from_files()`.

---

## Risks

1. **`serde_yaml` maintenance status:** The `serde_yaml` crate was formerly maintained by dtolnay but has been archived. The community fork `serde_yml` is the actively maintained replacement. The description file specifies `serde_yaml`, but the team should consider whether `serde_yml` is a better choice. Mitigation: verify crate status at implementation time; either crate provides the same API surface for basic YAML parsing.
2. **Name field ambiguity:** Some `pubspec.yaml` files might have the `name` field commented out or use non-standard formatting. Mitigation: `serde_yaml` handles standard YAML parsing robustly; commented-out fields are ignored by the parser.
3. **Large YAML files:** Some `pubspec.yaml` files in complex projects could be large. Mitigation: `serde_yaml` parses efficiently and only the `name` field is extracted; the rest is discarded.
4. **Module name collisions:** Multiple `pubspec.yaml` files in a monorepo could theoretically have the same `name:` value. Mitigation: the `modules` table has a `UNIQUE` constraint on `name`, so `INSERT OR IGNORE` will skip duplicates. This may need attention if duplicate names should be differentiated by path.
