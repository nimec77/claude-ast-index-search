# PRD: CS-1-1 -- Flutter/Dart Project Detection

**Status:** PRD_READY
**Ticket:** CS-1-1
**Created:** 2026-03-01

---

## Context / Idea

**Arguments:** CS-1-1 docs/phase/phase-1.md

`ast-index` is a multi-language code search CLI that detects project types via marker files and indexes source code into SQLite+FTS5. Currently, it supports Android, iOS, Perl, Frontend (JS/TS), Python, Go, Rust, and Bazel project types. Flutter/Dart projects are not recognized.

Phase 1 introduces Flutter project detection so that `ast-index` correctly identifies Flutter projects and their roots. The description file (`docs/phase/phase-1.md`) specifies the following tasks:

- **1.1** Add `Flutter` variant to `ProjectType` enum in `src/indexer.rs`
- **1.2** Add `pubspec.yaml` detection to `detect_project_type()` in `src/indexer.rs` -- return `ProjectType::Flutter` when present
- **1.3** Update `find_project_root()` in `src/indexer.rs` and `src/main.rs` -- walk up to the directory containing `pubspec.yaml`
- **1.4** Update `has_build_marker()` in `src/indexer.rs` -- return `true` for `pubspec.yaml` when `ProjectType` is `Flutter`

---

## Goals

1. Enable `ast-index` to detect Flutter projects by recognizing `pubspec.yaml` as a project marker file.
2. Ensure the project root is correctly resolved by walking up to the directory containing `pubspec.yaml`.
3. Integrate Flutter detection into the existing `ProjectType` enumeration and all functions that switch on project type.
4. Lay the groundwork for subsequent phases (Dart parsing, indexing, etc.) by establishing correct project identification.

---

## User Stories

1. **As a Flutter developer**, I want `ast-index index` to detect my project as a Flutter project, so that language-specific indexing behavior applies correctly.
2. **As a developer in a subdirectory** of a Flutter project, I want `ast-index` to walk up and find the project root (`pubspec.yaml` directory), so that I do not need to manually specify it.
3. **As a developer using `ast-index`**, I want the tool to correctly classify a project containing `pubspec.yaml` as `Flutter` (not `Unknown` or `Mixed`), so that downstream commands behave appropriately.

## Scenarios

### Scenario 1: Detect Flutter project type at root

**Given** a directory containing `pubspec.yaml`
**When** `ast-index index` is run in that directory
**Then** `detect_project_type()` returns `ProjectType::Flutter`

### Scenario 2: Find project root from subdirectory

**Given** a Flutter project with `pubspec.yaml` at `/projects/my_app/pubspec.yaml`
**When** `ast-index index` is run from `/projects/my_app/lib/src/`
**Then** `find_project_root()` returns `/projects/my_app`

### Scenario 3: Mixed project detection

**Given** a directory containing both `pubspec.yaml` and `package.json`
**When** `ast-index index` is run
**Then** `detect_project_type()` returns `ProjectType::Mixed`

### Scenario 4: Build marker recognition

**Given** a directory containing `pubspec.yaml`
**When** `has_build_marker()` is called for that path with `ProjectType::Flutter`
**Then** it returns `true`

### Scenario 5: Non-Flutter project is unaffected

**Given** a directory without `pubspec.yaml` but with `Cargo.toml`
**When** `ast-index index` is run
**Then** `detect_project_type()` still returns `ProjectType::Rust` (no regression)

## Constraints

1. **Files to modify (per description file):**
   - `src/indexer.rs` -- `ProjectType` enum, `detect_project_type()`, `find_project_root()`, `has_build_marker()`
   - `src/main.rs` -- `find_project_root()` (if duplicated there)
2. **Marker file:** `pubspec.yaml` is the sole marker for Flutter project detection.
3. **`has_build_marker()` signature:** Currently takes only `path: &Path`. Task 1.4 specifies it should return `true` for `pubspec.yaml` when `ProjectType` is `Flutter`, which implies the function may need a `ProjectType` parameter or an unconditional `pubspec.yaml` check. This is a design decision to resolve during implementation.
4. **Existing code gap in `find_project_root()`:** The function in `src/main.rs` (lines 1000-1039) currently checks for Gradle, Swift, `.xcodeproj`, and Bazel markers but has no check for `pubspec.yaml`. This must be added.
5. **`ProjectType::as_str()`:** The `as_str()` method on `ProjectType` must be extended to handle the new `Flutter` variant.
6. **Mixed detection logic:** The `detect_project_type()` function counts detected platforms and returns `Mixed` when more than one is found. The new `has_flutter` boolean must be included in this count array.

---

## Risks

1. **`has_build_marker()` design ambiguity:** The current signature `fn has_build_marker(path: &Path) -> bool` does not accept a `ProjectType`. Adding `pubspec.yaml` unconditionally could cause false positives for non-Flutter projects. Alternatively, changing the signature is a broader refactor. Mitigation: decide whether to add `pubspec.yaml` unconditionally (low risk since it is a specific marker) or pass `ProjectType` through.
2. **Overlap with Frontend projects:** Flutter projects may also contain `package.json` (e.g., for tooling). This would trigger `Mixed` detection. Mitigation: this is expected behavior per the existing multi-platform logic; no special handling needed in Phase 1.
3. **Duplicate `find_project_root()`:** The function exists in both `src/main.rs` and potentially `src/indexer.rs`. Both must be updated consistently. Mitigation: verify both locations during implementation.
