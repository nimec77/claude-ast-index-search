## Goals

1. Remove dead dependencies (`grep-matcher`, `parking_lot`) and dead-code suppression attributes from the codebase, reducing build time and maintenance burden.
2. Extract the repeated "index not found" guard pattern into a single `open_db_or_warn` helper, eliminating 24 copy-pasted guard blocks across 9 command files.
3. Deduplicate DB query row-mapping logic by introducing `SearchResult::from_row` and `RefResult::from_row`, and consolidate scoped/non-scoped query function pairs into thin-wrapper patterns.
4. Unify the `search_files` / `search_files_limited` pair by making the unlimited version delegate to the limited version, removing ~100 lines of duplicated WalkBuilder/channel code.
5. Extract a shared `configure_walk_ignores` helper to replace 5 duplicated arc/gitignore setup blocks scattered across indexer and command modules.
6. Replace magic numbers (file size limit, chunk size, walk depth) with named constants and extract a shared `build_thread_pool` helper to replace duplicated thread pool construction.
7. Deduplicate the grep-and-print boilerplate in `perl.rs` and `grep.rs` by extracting shared helpers, removing ~240 lines of repetitive code.
8. Split the 2992-line `indexer.rs` into focused sub-modules (`files`, `modules`, `resources`, `node_modules`) using Rust 2024 file-based module system, keeping the parent file lean.
9. Optionally split `db.rs` into sub-modules (`queries`), separating query functions from schema and connection management.
10. Maintain zero behavioral changes throughout -- all existing tests, clippy checks, and formatting checks must continue to pass after every sub-task.

## User Stories

1. **As a contributor**, I want dead dependencies removed from `Cargo.toml`, so that I am not confused by unused crates in the dependency list and build times are not inflated by unnecessary compilation.
2. **As a contributor**, I want the "index not found" guard logic centralized in a single helper, so that when the guard behavior needs to change I only need to update one location instead of 24.
3. **As a contributor**, I want DB row-mapping logic consolidated with `from_row` methods, so that adding a new field to `SearchResult` or `RefResult` requires updating only one place rather than 15+.
4. **As a contributor**, I want scoped and non-scoped query functions unified, so that I do not have to maintain two nearly-identical implementations for each query type.
5. **As a contributor**, I want `indexer.rs` split into sub-modules, so that I can work on file indexing, module parsing, resource indexing, or node_modules handling without navigating a 3000-line file.
6. **As a reviewer**, I want magic numbers replaced with named constants, so that the meaning of values like `1_000_000`, `500`, and `50` is immediately clear in code review.
7. **As a CI system**, I want `cargo test`, `cargo clippy -- -D warnings`, and `cargo fmt --check` to pass after every sub-task commit, so that the refactoring can be safely merged without regressions.

## Constraints

1. **No behavioral changes:** This is purely structural/cleanup work. No observable behavior of any command, query, or indexing operation may change. All existing tests must pass without modification to test assertions.
2. **Incremental commits:** Each sub-task (5.1-5.9) must be committed independently after passing all checks (`cargo test`, `cargo clippy -- -D warnings`, `cargo fmt --check`).
3. **Rust 2024 module system:** Tasks 5.8 and 5.9 must use the file-based module system (no `mod.rs` files). Child modules go under `src/indexer/` and `src/db/` respectively, with the parent file serving as the module root.
4. **Dependency on Phase 4:** Phase 4 must be complete before starting Phase 5.
5. **Task ordering:** Tasks 5.1-5.7 are independent of each other and can be done in any order. Task 5.5 depends on task 5.4 being complete (since 5.4 reduces a duplicated block in `commands/mod.rs` that 5.5 then replaces). Task 5.8 and 5.9 should be done last, after the deduplication tasks, so that the code being moved into sub-modules is already clean.
6. **Public API preservation:** All public functions and types must remain accessible from their current module paths (via re-exports from parent modules) to avoid breaking downstream callers.
7. **Memory tests single-threaded:** Memory regression tests must always be run with `--test-threads=1` due to the global allocator counter.
8. **Task 5.9 is optional:** The description marks task 5.9 as optional. It should only be undertaken if time permits and the benefit is clear.

## Risks

1. **Subtle behavioral changes from refactoring:** Even "pure structural" changes can inadvertently alter behavior if function signatures change, error handling paths differ, or re-exports are incomplete. Mitigation: run the full test suite after every sub-task; review each diff carefully for semantic differences.
2. **Re-export breakage after module split (Tasks 5.8, 5.9):** Moving functions into sub-modules and re-exporting them from the parent can break if any internal callers use full paths or if visibility modifiers are incorrect. Mitigation: use `pub use` re-exports in the parent module; run `cargo build` immediately after each move to catch compile errors.
3. **Guard helper behavior mismatch (Task 5.2):** The 24 existing guard blocks may not all be identical -- some may have slight variations in error messages, return types, or side effects. A single helper must accommodate all variants or the non-conforming ones must be handled separately. Mitigation: audit all 24 blocks before extracting the helper; parameterize the helper if needed.
4. **Merge conflicts with concurrent work:** Large-scale file moves (especially splitting `indexer.rs`) create high potential for merge conflicts if other branches modify the same files. Mitigation: coordinate with team; perform module splits as the last tasks; rebase frequently.
5. **Clippy lint changes between sub-tasks:** If the Rust toolchain is updated mid-phase, new clippy lints may surface that are unrelated to the refactoring. Mitigation: pin the Rust toolchain version for the duration of Phase 5.
6. **`from_row` performance (Task 5.3):** Introducing method calls where inline closures existed could theoretically affect query performance. Mitigation: the overhead is negligible (single function call vs. inline closure); verify with `cargo bench` if concerned.
