## Context / Idea

**Arguments:** CS-6-6 docs/phase/phase-6.md

This ticket covers Phase 6 of the project: large module decomposition. The goal is to reduce the 5 remaining 1000+ line files by extracting inline test modules to sibling files, splitting `main.rs` into focused modules, extracting Dart's error recovery subsystem, and deduplicating `find_capture` across 14 parser files. This is purely structural/cleanup work with no behavioral changes.

## Goals

1. Extract inline test modules from the 4 largest parser files (`dart.rs`, `csharp.rs`, `cpp.rs`, `typescript.rs`) into dedicated sibling `*_tests.rs` files, reducing source file sizes by 33-68% and making both production code and test code easier to navigate independently.
2. Split `main.rs` (~1043 lines) into focused modules by moving `Cli`/`Commands`/`find_project_root()` to `src/cli.rs` and `cmd_install_claude_plugin()` to `src/commands/management.rs`, reducing `main.rs` to ~330 lines (~68% reduction).
3. Extract Dart's error recovery subsystem (structs and functions at ~L855-1093) into a dedicated `dart_error_recovery.rs` submodule, isolating a self-contained feature for easier maintenance and testing.
4. Eliminate the duplication of `find_capture` across 14 tree-sitter parser files by introducing a single `pub(crate) fn find_capture` in `src/parsers/treesitter/mod.rs` and removing all 14 local copies.
5. Update project documentation (`CLAUDE.md`, `docs/tasklist.md`) to reflect the new file layout.
6. Maintain zero behavioral changes throughout -- all existing tests, clippy checks, and formatting checks must continue to pass after every sub-task.

---

## User Stories

1. **As a contributor**, I want parser test code separated into dedicated `*_tests.rs` files, so that I can navigate and edit production parser logic without scrolling through hundreds of lines of test fixtures.
2. **As a contributor**, I want `main.rs` focused on dispatch logic only, so that I can quickly understand the entry point without wading through CLI definition, project root detection, and plugin installation code.
3. **As a contributor**, I want Dart's error recovery logic in its own submodule, so that I can work on error recovery without navigating the full parser file and vice versa.
4. **As a contributor**, I want a single canonical `find_capture` function in the tree-sitter module root, so that when the function signature or behavior needs to change I only update one location instead of 14.
5. **As a reviewer**, I want each of the 5 remaining 1000+ line files reduced to under 800 lines, so that code reviews involve reasonably-sized, focused modules rather than monolithic files.
6. **As a CI system**, I want `cargo test`, `cargo clippy -- -D warnings`, and `cargo fmt --check` to pass after every sub-task commit, so that the decomposition can be safely merged without regressions.

## Constraints

1. **No behavioral changes:** This is purely structural/cleanup work. No observable behavior of any command, query, parsing, or indexing operation may change. All existing tests must pass without modification to test assertions.
2. **Incremental commits:** Each sub-task should be committed independently after passing all checks (`cargo test && cargo clippy -- -D warnings && cargo fmt --check`).
3. **Task ordering and dependencies:** Tasks 6.1.1-6.1.4 are independent of each other. Task 6.3 depends on 6.1.1 (Dart tests must be extracted before moving error recovery code). Task 6.4 depends on 6.1.1-6.1.4 (all test extractions must complete before deduplicating `find_capture`, since `find_capture` definitions may be interleaved with test code). Task 6.5 should be done last.
4. **Test file pattern:** Test extractions must use `#[cfg(test)] #[path = "<lang>_tests.rs"] mod tests;` pattern to maintain the same module structure and test discovery.
5. **Public API preservation:** All public functions and types must remain accessible from their current module paths (via re-exports or updated imports) to avoid breaking any callers. Specifically, `find_project_root()`, `Cli`, and `Commands` must remain usable from `main.rs` after being moved to `cli.rs`.
6. **Dependency on Phase 5:** Phase 5 must be complete before starting Phase 6.
7. **Memory tests single-threaded:** Memory regression tests must always be run with `--test-threads=1` due to the global allocator counter.
8. **find_capture visibility:** The shared `find_capture` must be `pub(crate)` in `mod.rs` and imported via `use super::find_capture;` in each parser file.

## Risks

1. **Test imports after extraction (Tasks 6.1.x):** Extracted test files may reference private functions, types, or `use` statements that were in scope when the test module was inline but are no longer in scope in a separate file. Mitigation: each extracted test file will need its own `use super::*;` or explicit imports; compile and run tests immediately after each extraction.
2. **find_capture signature variations (Task 6.4):** The 14 copies of `find_capture` may not all be byte-identical -- some may have slight variations in generics, lifetimes, or parameter types. Mitigation: compare all 14 implementations before extracting the shared version; if variations exist, the shared version must accommodate them or the outliers must be adapted.
3. **Circular or complex imports after main.rs split (Task 6.2):** Moving `Cli` and `Commands` to `cli.rs` while `main.rs` dispatches on them could create complex import chains, especially if `Commands` variants reference types from `commands/` modules. Mitigation: careful attention to module visibility and use of `pub(crate)` where needed.
4. **Dart error recovery internal dependencies (Task 6.3):** The error recovery code may reference parser-internal state or helper functions that are not cleanly separable. Mitigation: review the dependency graph of the error recovery structs/functions before extracting; if tight coupling exists, expose needed items via `pub(super)`.
5. **Merge conflicts with concurrent work:** Extracting tests and splitting files creates high potential for merge conflicts if other branches modify the same parser files. Mitigation: coordinate with team; complete all sub-tasks in a focused burst.
6. **IDE/tooling support for #[path] attribute:** Some Rust IDEs may not fully support the `#[path = "..."]` attribute for test modules, potentially degrading the development experience for contributors. Mitigation: this is a well-known Rust pattern; most modern IDEs (RustRover, VS Code with rust-analyzer) handle it correctly.
