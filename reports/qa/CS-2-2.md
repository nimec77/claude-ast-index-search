# QA Report: CS-2-2 -- YAML Parsing for Flutter Module Name Extraction

**Date:** 2026-03-01

**Tasklist status at review time:** IMPLEMENT_STEP_OK (all 5 tasks marked done)

## Summary

CS-2-2 adds `serde_yaml` to `Cargo.toml` and implements a new `pubspec.yaml` branch inside `index_modules_from_files()` in `src/indexer.rs`. The goal is to extract the `name:` field from Flutter `pubspec.yaml` files and insert Flutter module names into the `modules` SQLite table so they appear in `ast-index modules` output.

All implementation artifacts were inspected directly in source. The code matches the plan sketch exactly. Unit tests cover all five PRD scenarios plus two additional edge cases (empty name, malformed YAML). No schema changes were made. The dependency version resolved to `0.9.34-deprecated` (the last published version of the archived crate).

## Negative and Edge Cases

### NE-1: Missing `name:` field -- graceful skip (PRD Scenario 3)

**Test:** `test_pubspec_yaml_missing_name_field_is_skipped`
**Input:** `pubspec.yaml` containing only `version: 1.0.0\ndescription: No name field`
**Expected:** `count == 0`, no rows inserted
**Coverage:** Automated unit test -- PASS
**Implementation note:** The `PubSpec { name: Option<String> }` struct returns `None` for absent fields, triggering the skip correctly.

### NE-2: Malformed YAML -- graceful skip

**Test:** `test_pubspec_yaml_malformed_yaml_is_skipped`
**Input:** `pubspec.yaml` containing `name: [unclosed bracket`
**Expected:** `count == 0`, no rows inserted, no panic
**Coverage:** Automated unit test -- PASS
**Implementation note:** `if let Ok(pubspec) = serde_yaml::from_str::<PubSpec>(&content)` discards parse errors silently.

### NE-3: Empty string name -- graceful skip

**Test:** `test_pubspec_yaml_empty_name_is_skipped`
**Input:** `pubspec.yaml` with `name: ""`
**Expected:** `count == 0`, no rows inserted
**Coverage:** Automated unit test -- PASS
**Implementation note:** The `!mod_name.is_empty()` guard in the implementation handles this correctly.

### NE-4: Duplicate `name:` values across monorepo packages -- INSERT OR IGNORE

**Test:** No dedicated automated test
**Expected:** Second insertion is silently skipped due to `INSERT OR IGNORE` and the `UNIQUE` constraint on `modules.name`
**Coverage:** Manual check only -- the SQL uses `INSERT OR IGNORE`, consistent with all other module parsers
**Risk:** If two legitimate sub-projects share the same `name:`, only the first encountered is indexed. This is noted in the PRD as an accepted limitation.

### NE-5: Root-level `pubspec.yaml` produces empty module path

**Covered by:** PS-1 (asserts `rows[0].1 == ""`)
**Assessment:** Acceptable -- the module name comes from YAML content, so the empty path does not impair module identification.

### NE-6: Unreadable file (permission error)

**Test:** No automated test
**Expected:** `fs::read_to_string(path)` returns `Err`, the `if let Ok(content)` guard skips the file silently
**Coverage:** Code review only -- the guard is present in source at line 1110
**Risk:** LOW. Standard OS file permission failure; behavior is correct.

## Risk Zone

### RISK-1: `serde_yaml` crate is archived (MEDIUM)

**Detail:** The dependency resolved to `serde_yaml = "0.9.34-deprecated"`. The `-deprecated` version suffix in the published crate signals its archived status. This is a cosmetic concern for now -- the crate is fully functional for this use case -- but future security patches or Rust edition compatibility issues will not be addressed upstream.

**Recommendation:** Track as a known technical debt item. The PRD/Plan documents an ADR (`docs/adr/CS-2-2.md`) discussing `serde_yaml` vs `serde_yml`. If that ADR recommends migration to `serde_yml`, a follow-up ticket should be filed.

**Blocking for release:** No. The functionality is correct.

### RISK-2: No integration test for `ast-index modules` CLI output (LOW-MEDIUM)

**Detail:** All tests call `index_modules_from_files()` directly. The path from `is_module_file()` through the full `index_directory()` walk to `ast-index modules` output is not covered by an end-to-end test.

**Recommendation:** Manual smoke test on a real Flutter project before first production use. A future integration test would close this gap.

**Blocking for release:** No, given the manual check.

### RISK-3: Duplicate `name:` values produce silent data loss (LOW)

**Detail:** The `INSERT OR IGNORE` behavior means the second `pubspec.yaml` with a colliding `name:` is silently dropped. Dart naming conventions make this rare, but in adversarial monorepos it could mask modules.

**Blocking for release:** No. Consistent with established behavior of all other module parsers.

### RISK-4: CS-2-1 prerequisite coupling (LOW, already mitigated)

**Detail:** The `is_module_file()` change (CS-2-1) is confirmed present in source (line 443: `|| name == "pubspec.yaml"`). The prerequisite is satisfied.

**Blocking for release:** No.

## Final Verdict

**RELEASE with reservations**

The implementation is correct, well-tested at the unit level, and follows established patterns. All PRD scenarios are covered by automated tests. The two reservations are:

1. **`serde_yaml` archived crate status** -- not blocking, but must be tracked as technical debt. The ADR at `docs/adr/CS-2-2.md` should document the accepted risk and timeline for potential migration to `serde_yml`.
2. **Manual end-to-end verification required** -- a smoke test running `ast-index index` + `ast-index modules` on a real Flutter project must be completed and signed off before shipping to end users. This is a one-time manual check that does not require code changes.

No regressions were identified. The code is ready for integration once the two reservations above are addressed.
