# QA Report: CS-1-1 -- Flutter/Dart Project Detection

**Ticket:** CS-1-1
**Status:** PLAN_APPROVED / IMPLEMENT_STEP_OK
**QA Date:** 2026-03-01
**Prepared by:** QA Agent

---

## Summary

This ticket adds Flutter/Dart project detection to `ast-index` by recognizing `pubspec.yaml` as a project marker file. The implementation covers four code changes in `src/indexer.rs` and `src/main.rs`: a new `ProjectType::Flutter` enum variant, detection logic in `detect_project_type()`, project root resolution in `find_project_root()`, and build marker recognition in `has_build_marker()`. Three new unit tests were added. All six tasks in the tasklist are marked complete (`IMPLEMENT_STEP_OK`).

## Positive Scenarios

### PS-1: Flutter project detected at root (PRD Scenario 1)

**Precondition:** A directory contains `pubspec.yaml` as the only project marker.
**Action:** Call `detect_project_type()` on that directory.
**Expected:** Returns `ProjectType::Flutter`.
**Implementation status:** IMPLEMENTED. `has_flutter = root.join("pubspec.yaml").exists()` is evaluated and the `else if has_flutter { ProjectType::Flutter }` branch is present in `detect_project_type()` (indexer.rs lines 211, 247-248).
**Automated test:** `test_detect_flutter_project` -- creates an empty `pubspec.yaml` in a temp dir and asserts `ProjectType::Flutter`. PRESENT.

---

### PS-2: Project root found from subdirectory (PRD Scenario 2)

**Precondition:** A Flutter project has `pubspec.yaml` at its root; `ast-index index` is run from a nested subdirectory.
**Action:** `find_project_root()` walks up ancestors.
**Expected:** Returns the ancestor directory containing `pubspec.yaml`.
**Implementation status:** IMPLEMENTED. Block added at `src/main.rs` lines 1030-1033, placed after `.xcodeproj` check and before Bazel markers, matching the plan specification exactly.
**Automated test:** No dedicated unit test for `find_project_root()` with Flutter marker. Manual verification required (see Manual Checks section).

---

### PS-3: Build marker recognized (PRD Scenario 4)

**Precondition:** A directory contains `pubspec.yaml`.
**Action:** Call `has_build_marker()` on that directory.
**Expected:** Returns `true`.
**Implementation status:** IMPLEMENTED. `|| path.join("pubspec.yaml").exists()` appended to `has_build_marker()` boolean chain (indexer.rs line 144).
**Automated test:** `test_has_build_marker_pubspec` -- creates `pubspec.yaml` in a temp dir and asserts `true`. PRESENT.

---

### PS-4: `as_str()` returns correct display string

**Precondition:** `ProjectType::Flutter` enum variant exists.
**Action:** Call `.as_str()` on it.
**Expected:** Returns `"Flutter (Dart)"`.
**Implementation status:** IMPLEMENTED. `ProjectType::Flutter => "Flutter (Dart)"` present in `as_str()` match block (indexer.rs line 69).
**Automated test:** No dedicated test for `as_str()` on the Flutter variant. Manual verification or inline assertion recommended.

---

### PS-5: No regression for existing project types (PRD Scenario 5)

**Precondition:** A directory contains only `Cargo.toml` (no `pubspec.yaml`).
**Action:** Call `detect_project_type()`.
**Expected:** Returns `ProjectType::Rust`.
**Implementation status:** IMPLEMENTED. `has_flutter` is added to the count array but `pubspec.yaml` is not present, so `has_flutter = false`; the `else if has_rust` branch fires normally.
**Automated test:** Covered by existing `test_detect_rust_project` (or equivalent) plus `test_detect_unknown_project`. New code does not alter these branches.

## Negative and Edge Cases

### NC-1: Mixed Flutter + Frontend detection (PRD Scenario 3)

**Precondition:** Directory contains both `pubspec.yaml` and `package.json`.
**Action:** Call `detect_project_type()`.
**Expected:** Returns `ProjectType::Mixed` (both `has_flutter` and `has_frontend` are `true`, count = 2 > 1).
**Implementation status:** IMPLEMENTED. `has_flutter` is included in the count array at indexer.rs lines 214-227.
**Automated test:** `test_detect_mixed_flutter_and_frontend` -- creates both files and asserts `ProjectType::Mixed`. PRESENT.

---

### NC-2: Directory with no markers

**Precondition:** An empty directory (no recognized marker files).
**Action:** Call `detect_project_type()`.
**Expected:** Returns `ProjectType::Unknown`.
**Implementation status:** The new `has_flutter = false` for empty dirs; existing fallback `else { ProjectType::Unknown }` is unchanged.
**Automated test:** `test_detect_unknown_project` is present and unaffected.

---

### NC-3: `has_build_marker()` with no `pubspec.yaml`

**Precondition:** A directory contains none of the recognized markers.
**Action:** Call `has_build_marker()`.
**Expected:** Returns `false`.
**Implementation status:** The added `|| path.join("pubspec.yaml").exists()` evaluates to `false` when the file is absent; overall boolean chain returns `false`. No regression.
**Automated test:** Implicitly covered by existing negative tests for `has_build_marker()`.

---

### NC-4: `find_project_root()` when `pubspec.yaml` is not in any ancestor

**Precondition:** CWD and all ancestors lack `pubspec.yaml` and any other markers.
**Action:** `find_project_root()` walks all ancestors, finds no match.
**Expected:** Returns `cwd` (existing fallback at `src/main.rs` line 1042).
**Implementation status:** The new Flutter check block short-circuits with `return Ok(ancestor.to_path_buf())` only when the file exists; the fallback `Ok(cwd)` is unreachable otherwise.
**Automated test:** No dedicated test for this path. Low risk; pre-existing fallback behavior unchanged.

---

### NC-5: `pubspec.yaml` in a subdirectory (not at root) -- `detect_project_type()` behavior

**Precondition:** Root directory does NOT contain `pubspec.yaml`, but a subdirectory does.
**Action:** Call `detect_project_type(root)`.
**Expected:** `has_flutter = false`; does not return `ProjectType::Flutter` for the root (correct -- `pubspec.yaml` is a root-level marker check only).
**Implementation status:** CORRECT by design. `root.join("pubspec.yaml").exists()` checks only the immediate root, not recursively.
**Automated test:** Not explicitly tested. Risk: LOW.

---

### NC-6: `pubspec.yaml` alongside ALL other markers (full Mixed scenario)

**Precondition:** Directory contains `pubspec.yaml`, `Cargo.toml`, `package.json`, `go.mod`, etc.
**Action:** Call `detect_project_type()`.
**Expected:** Returns `ProjectType::Mixed` (count > 1).
**Implementation status:** CORRECT. `has_flutter` participates in the count; Mixed is returned when count > 1.
**Automated test:** Not explicitly tested, but the mechanism is the same as the existing `test_detect_mixed_project`.

---

### NC-7: Case sensitivity of `pubspec.yaml` filename

**Precondition:** A directory contains `PUBSPEC.YAML` or `Pubspec.Yaml` instead of the lowercase `pubspec.yaml`.
**Action:** Call `detect_project_type()` on macOS (case-insensitive HFS+) vs. Linux (case-sensitive ext4).
**Expected behavior difference:** On macOS the file would be found; on Linux it would not.
**Implementation status:** The code uses `root.join("pubspec.yaml")` (lowercase), which matches the Flutter convention. This is CORRECT per the Flutter standard (the file is always lowercase).
**Risk:** LOW on standard Flutter projects; negligible.

## Risk Zones

### RISK-1: `find_project_root()` has no automated test coverage for the new Flutter path (MEDIUM)

**Description:** The Flutter marker check in `find_project_root()` (`src/main.rs` lines 1030-1033) is not covered by any automated unit test. This function's correctness is critical for the user story "developer in a subdirectory." The change is simple (3 lines), but a regression here would silently cause root resolution failures for Flutter developers.

**Mitigation:** Manual end-to-end testing (Manual Check #2 above). Recommend adding a unit test for `find_project_root()` in a follow-up task.

---

### RISK-2: `as_str()` for `ProjectType::Flutter` not directly tested (LOW)

**Description:** `ProjectType::Flutter.as_str()` returns `"Flutter (Dart)"` per the implementation, but no test asserts this string. If the string is changed by accident in a refactor, no test would catch it.

**Mitigation:** Low risk for Phase 1. The display string is not used in any downstream logic that would cause functional failures. Recommend adding a test in Phase 2 when display output becomes more significant.

---

### RISK-3: `pubspec.yaml` unconditional in `has_build_marker()` -- false positives in non-Flutter monorepos (LOW)

**Description:** As documented in ADR CS-1-1, adding `pubspec.yaml` unconditionally means any directory containing it will be treated as a sub-project boundary in monorepo detection, regardless of parent project type.

**Mitigation:** `pubspec.yaml` is a highly specific Dart/Flutter marker. The risk of a non-Flutter monorepo having a stray `pubspec.yaml` in a non-project subdirectory is negligible. This is consistent with the existing treatment of `Makefile` and `CMakeLists.txt`. Accepted per ADR CS-1-1.

---

### RISK-4: Deviation from phase-1.md task 1.3 (RESOLVED / LOW)

**Description:** Phase-1.md task 1.3 states "Update `find_project_root()` in `src/indexer.rs` and `src/main.rs`." The function only exists in `src/main.rs`. The plan and tasklist correctly document this deviation.

**Mitigation:** The function is not in `src/indexer.rs` as stated in the phase description; only `src/main.rs` was updated. This is the correct behavior. No code fix needed. The deviation is fully documented and does not represent a gap in functionality.

---

### RISK-5: Flutter + Frontend mixed detection may surprise Flutter Web developers (LOW)

**Description:** Flutter Web projects (which do use `package.json` for tooling) will be classified as `ProjectType::Mixed` rather than `ProjectType::Flutter`. This is documented as expected behavior in PRD Scenario 3 and PRD Risk 2.

**Mitigation:** This is correct and intentional per the existing multi-platform detection architecture. Accepted for Phase 1.

## Final Verdict

**RELEASE WITH RESERVATIONS**

All four code changes are implemented correctly and match the plan specification. The three specified unit tests are present and cover the primary positive and mixed-detection scenarios. Existing tests for `Unknown` and `Mixed` project types are unaffected, providing confidence against regressions.

**Reservations:**

1. Task 1.3 (`find_project_root()` Flutter path in `src/main.rs`) has no automated test. This is the highest-risk gap because it covers a core user story (subdirectory root resolution). Manual end-to-end verification must be completed before release.

2. `ProjectType::Flutter.as_str()` returning `"Flutter (Dart)"` is not asserted in any test. This is low risk but leaves a minor gap.

3. Task 1.6 validation (`cargo test`, `cargo clippy`, `cargo fmt`) is marked complete in the tasklist but must be independently confirmed via CI or manual execution before release.
